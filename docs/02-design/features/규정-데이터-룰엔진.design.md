# 규정 데이터와 Rule Engine 설계 문서

> **요약**: 계획 문서 FR-01~FR-29를 구현 가능한 경계로 나눈다. 이 문서에서 확정되는 것은 **누가 무엇을 소유하는가**와 **엔진이 어떤 순서로 실행되는가** 둘이다.
>
> **프로젝트**: Replay_Lab
> **작성일**: 2026-08-06
> **상태**: Draft
> **선행 문서**: [계획 문서](../../01-plan/features/규정-데이터-룰엔진.plan.md) · [README](../../../README.md)

---

## 1. 이 문서가 답하는 것

계획 문서는 무엇을 만들지를 정했고 SSOT의 소유자까지 정했다(FR-28).
남은 것은 **그 소유자들이 실제로 어떤 파일이고 어떤 순서로 맞물리는가**다.

| # | 막혀 있던 것 | 이 문서의 결정 | 절 |
|:-:|---|---|:-:|
| 1 | `RuleSet`의 내부 형태가 `cite()` 하나뿐이라 VAR 활성 집합을 실을 자리가 없다 | 계층 배열을 가진 **동결된 값**. 인터페이스가 아니다 | 5 |
| 2 | `shared-types`가 비어 있어 어휘의 SSOT가 아직 README에 있다 | 첫 파일의 내용과 **방향이 뒤집히는 커밋의 구성**을 확정 | 4 |
| 3 | README의 `evaluatePush` 스케치는 조기 반환이 4개인데, 그 경로들이 `accounts`를 채우지 않는다 | `accounts` 구성을 게이트보다 **앞으로** 옮긴다 | 6 |

3번은 스케치를 그대로 구현하면 FR-26이 깨진다는 뜻이다. 6.2에서 따로 다룬다.

## 2. 소유자 지도

FR-28에서 정한 세 소유자를 파일 단위로 내린 것이다. 새 결정이 아니라 주소를 붙인 것이다.

| 소유하는 것 | 어디 | 판본에 따라 변하나 | 예 |
|---|---|:---:|---|
| **어휘** — 엔진이 쓸 수 있는 낱말의 닫힌 집합 | `packages/shared-types/src/vocabulary.ts` | 아니오 | `Decision` · `Severity` · `VarCategory` · `Relevance` |
| **활성 집합** — 그 판본에서 열려 있는 부분집합과 조항 본문 | `packages/rule-data/{authority}/{edition}/` | 예 | 재심의 대상 범주, 밀기 결정 표, 조항 인용 |
| **구조 불변식** — 행이 성립하려면 참이어야 하는 것 | `packages/database/` 마이그레이션 | 아니오 | 인용 최소 1개, `NOT NULL`, 외래키 |

여기에 하나를 더 정한다. **`rule-data/`의 JSON이 정의이고 `rules` 테이블은 적재된 사본이다.**

방향이 이쪽인 이유는 두 가지다. 엔진은 DB 없이 순수 함수로 실행되어야 하고(NFR·DoD),
픽스처 검사는 엔진 구현 전부터 CI에서 돈다. 정의가 DB에 있으면 둘 다 DB를 띄워야 한다.
FR-05의 "적재"는 JSON에서 DB로 가는 단방향 작업이며, 반대 방향 경로는 만들지 않는다.

```
rule-data/*.json  ──적재(FR-05)──▶  rules 테이블  ──조회──▶  결과 화면
      │
      └──loadRuleSet()──▶  RuleSet  ──주입──▶  rule-engine
```

## 3. 패키지 경계

### 3.1 의존 방향

```
shared-types  ◀── rule-data
     ▲              ▲
     │              │  (adapter가 주입)
     └───────── rule-engine
                    ▲
                    │
              database / apps / workers
```

`rule-engine`은 `rule-data`를 **import 하지 않는다.** 판본 문자열이 엔진 코드에 들어오는 순간
FR-21("코드 변경 0")을 검증할 방법이 없어진다. 엔진은 `shared-types`만 알고, 규정은 인자로 받는다.

이 규칙은 문장이 아니라 검사로 지킨다.

```bash
# DoD 항목
grep -rn "2025-26\|2026-27" packages/rule-engine/src   # 결과 0건
```

### 3.2 포트 세 개

헥사고날을 이름으로 도입하는 게 아니라, 재현성 NFR이 이미 요구하는 경계를 그대로 적은 것이다.

| 방향 | 포트 | 시그니처 | 어긋나면 |
|---|---|---|---|
| 인바운드 | 평가 | `evaluate(facts: PushFacts, rules: RuleSet, options: CompetitionOptions): EvaluationResult` | — |
| 아웃바운드 | 규정 | `RuleSet` (5절) | 판본이 코드에 박힌다 |
| 아웃바운드 | 판본 해석 | `resolveRuleVersion(competition, matchDate): EditionRef \| "UNKNOWN_RULE_VERSION"` | FR-12의 미스 케이스를 표현할 곳이 없다 |

`competition_options`가 `RuleSet`이 아니라 **별도 인자**인 것이 FR-24의 요점이다.
IFAB가 열어둔 것과 K리그가 채택한 것은 다른 축이고, 픽스처 `var-14`/`var-15`가 같은 판본에서
채택 여부만 뒤집어 다른 결과를 요구한다. 같은 객체에 넣으면 그 독립성이 표현되지 않는다.

```ts
type CompetitionOptions = {
  cornerKickReview: boolean | null;   // null = 확인되지 않음, false와 다르다
};
```

`null`과 `false`를 나누는 이유는 `var-21`이다. 미채택은 사실이고 미확인은 사실이 아니다.
미확인일 때 엔진은 `reviewable`을 정하지 않고 `UNKNOWN_COMPETITION_OPTION`을 반환한다.

## 4. `shared-types` — 어휘의 정의

### 4.1 파일 구성

```
packages/shared-types/src/
├── vocabulary.ts     ← 판본과 무관한 열거형. FR-28의 SSOT
├── facts.ts          ← Observed<T>, PushFacts, CompetitionOptions
├── result.ts         ← EvaluationResult 와 그 구성 타입
└── index.ts
```

`vocabulary.ts`만 SSOT이고 나머지 둘은 그것을 쓰는 쪽이다.
한 파일에 몰아넣지 않는 이유는, 검사기가 "어휘가 어디까지인가"를 파일 경계로 알 수 있어야 하기 때문이다.

### 4.2 `vocabulary.ts`에 들어가는 것

README 8절·11절에서 옮겨오는 값들이다. 옮기는 것이지 새로 만드는 것이 아니다.

```ts
export const DECISION = ["FOUL", "NO_FOUL", "NORMAL_CONTACT", "INCONCLUSIVE", "OUT_OF_SCOPE"] as const;
export const SEVERITY = ["CARELESS", "RECKLESS", "EXCESSIVE_FORCE"] as const;
export const RELEVANCE = ["PRIMARY", "SUPPORTING", "COUNTER_READING"] as const;
export const AUTHORITY = ["IFAB", "KFA", "KLEAGUE"] as const;

export const VAR_CATEGORY = ["GOAL_NO_GOAL", "PENALTY_NO_PENALTY", "RED_CARD",
                             "MISTAKEN_IDENTITY", "CORNER_KICK", "NONE"] as const;
export const VAR_THRESHOLD_MET = ["MET", "NOT_MET", "UNDETERMINED"] as const;
export const VAR_INTERVENTION = ["NO_INTERVENTION", "OVERTURNED", "CONFIRMED"] as const;
export const VAR_REVIEW_PROCEDURE = ["OFR", "VAR_ONLY", "NONE"] as const;
// … 8절 DDL의 나머지 열거형도 같은 형태

export type Decision = (typeof DECISION)[number];
export type VarCategory = (typeof VAR_CATEGORY)[number];
```

**배열 상수를 먼저 두고 타입을 파생시키는 것이 요점이다.** 유니온 타입만 쓰면 값의 목록이
런타임에 존재하지 않아 검사기가 읽을 수 없고, 그러면 SSOT라고 선언해 놓고 기계가 확인하지 못한다.

`VAR_CATEGORY`에 `CORNER_KICK`이 들어 있는 것이 어휘와 활성 집합의 차이를 보여주는 자리다.
2025-26에서 이 값은 **어휘에 있고 활성 집합에 없다.** `var-14`가 이 상태를 요구한다 —
채택하지 않았다고 말하려면 그 이름을 알아야 한다.

### 4.3 SSOT가 넘어가는 커밋

지금 어휘의 정의는 README에 있다. `vocabulary.ts`가 생기는 순간 두 소유자가 겹치므로,
**아래 셋을 한 커밋에 함께 넣는다.**

| # | 변경 | 안 하면 |
|:-:|---|---|
| 1 | `vocabulary.ts` 추가 | — |
| 2 | `check/enums.mjs`가 README 대신 `vocabulary.ts`를 읽음 | 픽스처가 옛 정의를 통과 |
| 3 | `check/readme.mjs` 검사 5의 방향을 뒤집음 — README 8절·11절을 `vocabulary.ts`에 맞춰 검사 | README가 조용히 뒤처짐 |

3번은 검사의 삭제가 아니라 방향 전환이다. 지금은 8절↔11절을 서로 비교하지만,
전환 후에는 양쪽 모두를 `vocabulary.ts`와 비교한다. 비교 대상이 셋으로 늘고 기준이 하나가 된다.

이 커밋 이후 README의 열거형 목록은 **읽는 사람을 위한 사본**이고, 틀리면 CI가 잡는다.

## 5. `RuleSet` — 적재가 끝난 값

### 5.1 인터페이스가 아니라 값이다

README의 스케치는 `cite(conceptKey): RuleCitation[]` 하나였다. 여기서 두 가지를 확정한다.

**첫째, `RuleSet`은 엔진 실행 전에 완전히 구체화되고 동결된다.**
`cite()`를 게으른 조회로 만들면 실행 중에 파일이나 DB를 읽게 되는데,
이것은 `packages/rule-engine`의 의존성 검사(외부 의존 0)를 **통과하면서** 재현성 NFR을 깬다.
주입받는 객체가 I/O를 하면 엔진은 순수 함수가 아니다.

```ts
// 적재는 어댑터의 일이고, 엔진이 받는 것은 이미 끝난 결과다
export function loadRuleSet(ref: EditionRef): RuleSet;   // packages/rule-data
```

`cite`는 이미 만들어진 `Map` 위의 동기 조회이며 동결된 배열을 반환한다.

**둘째, `RuleSet`은 계층 배열을 가진다.** `accounts[]`가 IFAB·KFA·K리그를 각각 실어야 하므로
(FR-26·FR-27) 판본 하나로는 주소가 나오지 않는다.

```ts
type RuleLayer = {
  authority: Authority;
  edition: string;                       // "2025-26" | "kleague1-2026"
  verification: "CONFIRMED" | "INFERRED";   // FR-23
  citations: Readonly<Record<string, readonly RuleCitation[]>>;
  requires: Readonly<Record<string, readonly string[]>>;   // conceptKey → 필요한 사실값
};

type RuleSet = {
  layers: readonly RuleLayer[];
  varCategories: readonly VarCategoryRule[];
  pushTable: readonly PushRule[];
  conflicts: readonly LayerConflict[];
  cite(conceptKey: string): readonly RuleCitation[];   // 전 계층을 모은다
};
```

`verification`이 계층에 붙는 이유는 미결 질문 1a 때문이다. 대회요강의 판본 지정 범위가
추론 상태이므로 K리그 계층만 `INFERRED`이고 IFAB 계층은 `CONFIRMED`다.
계층별로 다른 값을 가질 수 있어야 한다.

### 5.2 폴더 구조 — 계획 문서 6.3의 정정

계획 문서는 `rule-data/2025-26/`처럼 판본을 최상위에 두었다. **권위를 최상위로 올린다.**

```
packages/rule-data/
├── ifab/
│   ├── 2025-26/{edition,citations,var-categories,push-rules}.json
│   └── 2026-27/{동일 4개}
├── kleague/
│   ├── kleague1-2026/{edition,citations}.json
│   └── kleague2-2026/{edition,citations}.json
└── kfa/                       ← 미확보. 빈 폴더를 만들지 않는다
```

판본만으로는 `accounts[]`의 주소가 나오지 않는다는 것이 이유다.
`rules/`(원문)와 같은 배치가 되므로 적재 스크립트의 대응도 1:1이 된다.

**`kfa/`를 빈 폴더로 만들지 않는다.** 빈 폴더는 "확인했는데 없음"과 "아직 안 봄"을 구분하지 못한다.
KFA 계층이 없는 동안 `accounts`는 2개 계층만 싣고, 그것이 정직한 상태다.

### 5.3 VAR 범주 데이터 — FR-21과 FR-24가 걸리는 자리

```jsonc
// ifab/2026-27/var-categories.json
{
  "categories": [
    { "key": "GOAL_NO_GOAL",        "review_procedure": "OFR", "concept_key": "VAR_CATEGORY_GOAL" },
    { "key": "PENALTY_NO_PENALTY",  "review_procedure": "OFR", "concept_key": "VAR_CATEGORY_PENALTY" },
    { "key": "RED_CARD",            "review_procedure": "OFR", "concept_key": "VAR_CATEGORY_RED_CARD" },
    { "key": "MISTAKEN_IDENTITY",   "review_procedure": "VAR_ONLY", "concept_key": "VAR_CATEGORY_IDENTITY" },
    { "key": "CORNER_KICK",         "review_procedure": "OFR", "concept_key": "VAR_CATEGORY_CORNER",
      "requires_competition_option": "corner_kick_review" }
  ],
  "window_closes_on": "PLAY_RESTARTED",
  "window_exceptions": ["MISTAKEN_IDENTITY", "VIOLENT_CONDUCT"]
}
```

2025-26 파일은 같은 형태에서 `CORNER_KICK` 원소가 없다. **파일 하나의 원소 개수 차이가
FR-21의 4↔5 전부다.** 엔진에는 개수도 목록도 들어 있지 않다.

`requires_competition_option` 한 필드가 FR-24를 데이터로 만든다.
이 필드가 있는 범주는 `CompetitionOptions`에서 해당 값이 참일 때만 활성 집합에 들어가고,
`null`이면 `UNKNOWN_COMPETITION_OPTION`이 된다.

`window_closes_on: "PLAY_RESTARTED"`가 데이터인 이유는 VAR 창을 닫는 것이 주심의 선언이 아니라
**재개**라는 점이 규정에서 오는 사실이기 때문이다. 코드에 두면 이것이 우리 정책처럼 보인다.

### 5.4 밀기 규칙 — 미니 DSL이 아니라 결정 표

FR-06은 "코드 하드코딩 금지"를 요구하지만, 규칙 하나를 위해 언어를 만드는 것은 과하다.
**조건과 결과의 순서 있는 표**로 표현한다.

```jsonc
// ifab/2025-26/push-rules.json
{
  "concept_key": "LAW_12_PUSHING",
  "rules": [
    { "when": { "contact_detected": false },
      "then": { "decision": "NO_FOUL", "restart": "NONE" }, "cite": "LAW_12" },

    { "when": { "severity": "uncertain" },
      "then": { "decision": "INCONCLUSIVE", "inconclusive_reason": "SEVERITY_UNDETERMINED" }, "cite": "LAW_12" },

    { "when": { "opponent_displacement": ["uncertain", "possible"] },
      "then": { "decision": "INCONCLUSIVE", "inconclusive_reason": "SEVERITY_UNDETERMINED" }, "cite": "LAW_12" },

    { "when": { "opponent_displacement": "none", "severity": "CARELESS" },
      "then": { "decision": "NORMAL_CONTACT", "restart": "NONE" }, "cite": "LAW_12" },

    { "when": {},
      "then": { "decision": "FOUL", "restart_by_area": true, "disciplinary_by_severity": true }, "cite": "LAW_12" }
  ],
  "disciplinary_by_severity": { "CARELESS": "NONE", "RECKLESS": "CAUTION", "EXCESSIVE_FORCE": "SEND_OFF" }
}
```

표를 위에서부터 훑고 처음 맞는 행을 쓴다. `when: {}`은 기본 행이며 마지막에 하나만 둔다.
값이 배열이면 그중 하나와 일치하는지를 본다. 그 이상의 연산자(비교·논리)는 **넣지 않는다** —
필요해지는 시점이 곧 판단이 규정에서 코드로 새고 있다는 신호이므로, 그때 다시 설계한다.

`disciplinary_by_severity`가 데이터인 것이 중요하다. 무모→경고, 과도한 힘→퇴장은 Law 12의 내용이지
우리의 정책이 아니다.

**게이트는 이 표에 넣지 않는다.** 카메라·속도 게이트는 규정의 내용이 아니라
**관측 가능성에 대한 판단**이고, 이 시스템이 스스로 지는 규율이다. 코드에 두고 인용만 데이터에서 가져온다.
표에 섞으면 판본 데이터를 고쳐서 게이트를 끌 수 있게 되는데, 그것이 계획 문서 5절의
"속도 게이트를 우회하고 싶어짐" 위험이 실현되는 정확한 경로다.

## 6. 엔진 내부

### 6.1 실행 순서

```
1. 판본 해석      resolveRuleVersion(competition, match_date)
                  └ 매핑에 없으면 UNKNOWN_RULE_VERSION 으로 종료 (FR-12)
2. 규정 적재      loadRuleSet(ref) → 동결된 RuleSet          ← 여기까지가 어댑터

3. accounts 구성   각 계층 × 이 상황의 conceptKey → AuthorityAccount[]
4. conflicts 수집  계층 간 갈리는 지점 (FR-27)
5. 사실 요구 대조   FactRequirement[] — 무엇이 확정됐고 무엇이 막혔는가

6. 카메라 게이트   camera_sufficiency = low  → INCONCLUSIVE(CAMERA_INSUFFICIENT)
7. 속도 게이트     severity.observed_at_speed ≠ NORMAL → INCONCLUSIVE(SLOW_MOTION_ONLY)
8. 결정 표 적용    push-rules.json 순차 매칭

9. VAR 4게이트     범주 → 시한 → 문턱 → 절차 (각각 별도 필드)
10. 관측 비교      observed_* 대 추천 판정 → decision_match
11. fact_signature 생성
```

### 6.2 `accounts`가 게이트보다 앞에 있는 이유

**README의 `evaluatePush` 스케치를 그대로 구현하면 FR-26이 깨진다.**
그 스케치에는 조기 반환이 네 곳 있고(`cameraSufficiency`, `contactDetected`,
`observedAtSpeed`, `uncertain`), 각 반환은 `inconclusive(rules, ...)` 또는
`decide(...)`를 부른다. 이 헬퍼들이 `accounts`를 채우려면 **네 곳 모두에서 잊지 않아야** 한다.

`push-10`은 바로 이것을 검사한다 — 사실값이 막혀도 `accounts`는 비어 있을 수 없다.
잊지 않는 것에 의존하는 설계는 언젠가 잊는다.

그래서 3~5단계를 6단계 앞으로 옮긴다. `accounts`·`conflicts`·`blockedFrom`은
**게이트 이전에 이미 만들어져 있고**, 게이트는 `decision` 계열 필드만 결정한다.

```ts
function evaluate(facts, rules, options): EvaluationResult {
  const base = buildAccounts(facts, rules);   // accounts · conflicts · narrowedTo · blockedFrom

  const gate = checkGates(facts, rules);
  if (gate) return { ...base, ...gate, varAssessment: assessVar(facts, rules, options) };

  const outcome = applyTable(facts, rules.pushTable);
  return { ...base, ...outcome, varAssessment: assessVar(facts, rules, options) };
}
```

`buildAccounts`는 사실값이 하나도 확정되지 않아도 동작한다.
**규정이 무엇을 요구하는지는 영상과 무관하게 말할 수 있기 때문이다.**
막힌 사실은 `blockedFrom`에 `blockedBy: CAMERA | SPEED | NOT_IN_FOOTAGE`로 남는다.

`varAssessment`가 양쪽 경로에 다 있는 것도 같은 이유다. VAR 네 게이트는 밀기 판정의
하위 결과가 아니라 별도 축이며, `var-19`가 항상 네 필드가 나오는지를 검사한다.

### 6.3 모듈 — 계획 문서 6.3의 파일 목록 정정

파일 하나를 더하는 것이 아니라 **네 개를 바꾼다.** 바뀐 것을 각각 적는다.

| 계획 문서 | 이 설계 | 왜 |
|---|---|---|
| `evaluate-push.ts` | `evaluate.ts` + `build-accounts.ts` | 6.2 — `accounts` 구성이 게이트보다 앞이라 같은 파일에 둘 수 없다 |
| `interpreter.ts` | `apply-table.ts` | 5.4에서 미니 DSL을 만들지 않기로 했다. "인터프리터"는 없는 것의 이름이다 |
| `speed-gate.ts` | `gates.ts` | 게이트는 카메라·속도 둘인데 이름이 하나만 말하고 있었다 |
| `types.ts` (`Observed<T>`·`Decision`) | 삭제 — `shared-types`로 | 4.1에서 어휘의 소유자를 정했다. 남겨두면 소유자가 둘이 된다 |

정정 후 목록이다.

| 파일 | 책임 | 관련 |
|---|---|---|
| `evaluate.ts` | 순서 조립. 판단하지 않는다 | FR-07 |
| `build-accounts.ts` | 계층별 조항 선택, 사실 요구 대조, 충돌 수집 | FR-26·FR-27 |
| `gates.ts` | 카메라·속도 게이트 | FR-08·FR-16 |
| `apply-table.ts` | 결정 표 해석 | FR-06·FR-11 |
| `var-assessment.ts` | 네 게이트 각각 | FR-10·FR-21·FR-24 |
| `fact-signature.ts` | 서명 생성 | FR-20 |

`evaluate.ts`가 판단을 하지 않는 것이 검증 지점이다. 이 파일에 `if (facts.severity...)`가
생기기 시작하면 판단이 표에서 코드로 새고 있다는 뜻이다.

### 6.4 `fact_signature`

`var-20`이 두 가지를 요구한다 — 결정적일 것, 그리고 경기·팀·선수·심판 식별자를 포함하지 않을 것.

```
정규화된 사실 키·값 쌍을 키 이름으로 정렬 → 안정 직렬화 → SHA-256
```

입력에 들어가는 것은 `PushFacts`의 **값**뿐이고 `observed_at_speed`·`shot_ids`는 제외한다.
같은 사실 조합이 어느 경기에서 나오든 같은 서명을 가져야 선례 조회가 성립하는데,
샷 id는 경기마다 다르므로 넣으면 서명이 매번 달라진다.

## 7. `Observed<T>`의 경계

계획 문서 8절이 설계에서 먼저 정하라고 지목한 항목이다.

**관측된 사실은 전부 래핑하고, 관측의 조건은 래핑하지 않는다.**

```ts
type PushFacts = {
  contactDetected: Observed<boolean>;
  severity: Observed<Severity | "uncertain">;
  opponentDisplacement: Observed<"none" | "possible" | "clear" | "uncertain">;
  insidePenaltyArea: Observed<boolean>;
  cameraSufficiency: "low" | "medium" | "high";   // 래핑하지 않는다
};
```

`cameraSufficiency`가 예외인 것은 자의적 선택이 아니다.
이 값은 **관측 조건 그 자체**이며, 자기 자신을 관측 조건으로 가질 수 없다.
래핑하면 `cameraSufficiency.observedAtSpeed`가 생기고 그 값의 카메라 충분성을 또 물어야 한다.

이 선을 그으면 예외 목록이 생기지 않는다. 계획 문서가 경계한 것이 바로 그것이다 —
"어떤 값이 예외인지가 또 하나의 규칙이 된다".

## 8. DB 스키마 — 1단계 범위

1단계에서 엔진은 DB를 쓰지 않는다. 스키마를 지금 만드는 이유는 FR-05 적재와
FR-25 기록 때문이며, 나중에 뒤집는 비용이 훨씬 크기 때문이다.

| 테이블 | 1단계 용도 |
|---|---|
| `rules` | FR-05 적재 대상. `rule-data/`의 사본 |
| `competition_rule_versions` | FR-04·FR-12. `(competition, match_date)` 조회 |
| `decision_results` | FR-29. 인용 JSONB + `created_at`, 갱신 없음 |
| `official_verdicts` | FR-25. 라벨 사례 3건 |

### 8.1 `CHECK`은 구조에만 건다

```sql
-- 건다: 구조 불변식
citations JSONB NOT NULL CHECK (jsonb_array_length(citations) >= 1)

-- 걸지 않는다: 값 열거형
-- var_category TEXT CHECK (var_category IN ('GOAL_NO_GOAL', ...))   ← 금지
```

값 열거형에 `CHECK`을 걸면 판본 추가가 마이그레이션이 되어 FR-21이 깨진다(FR-28).
컬럼은 `TEXT`이고, 값의 유효성은 엔진이 `vocabulary.ts`로 이미 보장한 뒤에 들어온다.
DoD에 `grep -rn "CHECK" packages/database` 항목이 있는 이유다.

### 8.2 ORM — Drizzle 확정

계획 문서 6.2가 잠정으로 남긴 항목이다. **Drizzle로 확정한다.**

FR-29가 JSONB `CHECK`과 생성 열(`GENERATED ALWAYS AS ... STORED`)을 요구하는데,
Drizzle은 마이그레이션이 SQL 그대로라 둘을 스키마 정의에 함께 둘 수 있다.
Prisma는 이 둘을 스키마 언어로 표현하지 못해 수동 SQL 마이그레이션을 섞게 되고,
그러면 스키마 파일이 실제 스키마의 일부만 담게 된다 — 소유자가 둘로 갈리는 것과 같은 문제다.

1단계에서 이 선택이 엔진에 영향을 주지 않는 것도 확인해 둔다. 엔진은 DB를 모른다.

## 9. 테스트 설계

### 9.1 러너의 두 경로

픽스처는 `cases[]`와 `invariants[]`로 갈라져 있다(README 13절). 러너도 갈린다.

```
cases[]      원소마다 evaluate(given.facts, ruleSet, options) 1회 → expect 대조
invariants[] 위 결과를 전부 모은 뒤 applies_to 범위에 대해 사후 검사
```

불변식 4건이 검사하는 것은 개별 정답이 아니라 **산출물의 형태**다.

| id | 검사 | 깨지면 |
|---|---|---|
| `push-09` | 모든 결과에 인용 ≥ 1 | 근거 없는 결론이 나온다 |
| `push-10` | 사실이 막혀도 `accounts` 비지 않음 | `INCONCLUSIVE`가 빈 화면이 된다 |
| `var-19` | 네 게이트가 별도 필드 | 이유가 접혀 결론만 남는다 |
| `var-20` | 서명이 결정적·식별자 없음 | 선례 조회가 무의미해지고 개인정보가 샌다 |

### 9.2 FR-21 검증

같은 사실값을 두 `RuleSet`에 각각 넣어 결과가 갈리는지를 본다.
`var-12`/`var-13`이 이미 이 쌍이며, 테스트가 확인할 것은 **엔진 코드가 두 실행에서 동일하다는 것**이다.

### 9.3 재현성

동일 `(facts, ruleSet, options)`로 2회 실행해 깊은 동등성을 본다.
`RuleSet`이 동결되어 있으므로 두 실행 사이에 규정이 변할 수 없다는 것이 이 테스트의 전제이고,
`Object.isFrozen` 검사를 `loadRuleSet`의 반환값에 대해 함께 건다.

## 10. 구현 순서

앞 단계가 뒤 단계의 입력을 확정하는 순서다.

| # | 작업 | 산출물 | 선행 |

| 2 | `rule-data` 스키마 확정 + `ifab/2025-26` 작성 | JSON 4종 | 1 |
| 3 | `loadRuleSet` + 동결 | `RuleSet` | 2 |

8번을 7번 뒤에 두는 것도 의도다. 러너가 먼저 돌아야 판본 교체가 실제로 결과를 바꾸는지
확인할 수 있고, 그 전에 2026-27을 만들면 통과 여부를 눈으로 판단하게 된다.

## 11. 미결 사항

계획 문서 8절의 목록에서 **설계 때문에 새로 열린 것만** 적는다.

| # | 질문 | 차단 대상 | 지금의 처리 |
|:-:|---|---|---|
| D1 | Law 12 발췌 범위 — 조 전체인가 밀기 관련 항만인가 | FR-05 작업량 | 밀기 관련 항 + 12조 서문. 넓히는 것은 나중에 가능하고 좁히는 것은 아니다 |
| D2 | `conceptKey` 명명 — `LAW_12_PUSHING` 같은 개념 단위인가 `LAW_12_1` 같은 조항 단위인가 | `citations.json` 키 | **개념 단위.** 조항 번호는 판본마다 움직이는데 개념은 안 움직인다 |
| D3 | `requires`(조항이 요구하는 사실값)를 계층별로 다르게 쓸 일이 있는가 | `RuleLayer.requires` 형태 | 계층별로 둔다. K리그가 IFAB보다 더 요구하는 경우를 지금은 모르지만, 합쳐 두면 나중에 가를 수 없다 |

D2는 이 문서에서 답한다. 조항 번호를 키로 쓰면 2026/27에서 범주 `c`의 이름이 바뀐 것 같은
변경이 키를 깨뜨리고, 그러면 판본 교체가 코드 변경이 된다.

계획 문서의 미결 1a·2·3·4·5는 그대로 열려 있으며 이 설계는 그것들을 닫지 않는다.
1a는 `RuleLayer.verification`으로, 5는 `CompetitionOptions.cornerKickReview: null`로
**모른다는 사실을 값으로 들고 가는** 방식으로 처리된다.
