# 규정 데이터와 Rule Engine 계획 문서

> **요약**: 영상 처리 없이, 밀기 1개 유형 × 1개 판본으로 "사실값 → 판정 → 근거 조항"이 끝까지 이어지는 최소 수직 관통을 만든다.
>
> **프로젝트**: Replay_Lab (K리그 규정 기반 영상 판정 분석 시스템)

## 1. 개요

### 1.1 목적

판정 결과가 **규정 조항까지 역추적 가능한 결정론적 룰 엔진**을 먼저 완성한다.

이 프로젝트의 신뢰도는 "AI가 오심이라고 했다"가 아니라 "어느 판본 몇 조에 따라 이렇게 본다"에서 나온다.
따라서 영상 자동화보다 **규정 데이터 구조와 판정 근거 경로**를 먼저 세운다.

### 1.2 배경

README 18절의 방향에 따른다.

- 영상 모델은 교체될 수 있지만 규정 계층은 유지되어야 한다
- 규칙 엔진이 먼저 있어야 영상 모델이 채워야 할 사실값의 스펙이 확정된다
- 반대로 하면 모델이 뽑아준 값에 맞춰 판정 로직을 끼워 맞추게 된다

1단계에서 UI와 파서를 함께 진행하지 않는 이유는 3절 범위에서 다룬다.

FR-26·FR-27은 산출물의 형태에 대한 요구사항이다.
이 시스템이 답하는 질문은 "이 판정이 맞았나"가 아니라 "이 상황에 대해 규정은 무엇을 말하는가"이기 때문이다 (README 1절).
FR-26이 없으면 `INCONCLUSIVE`가 빈 화면이 된다 — 영상으로 사실을 못 정해도 규정이 무엇을 요구하는지는 말할 수 있는데도 아무 말을 못 하게 된다.
FR-27이 없으면 층위가 갈릴 때 코드가 임의로 한쪽을 고르게 된다.

FR-28은 FR-21이 성립하기 위한 전제다.
`var_category`에 DB `CHECK`을 걸면 판본이 하나 느는 것이 마이그레이션이 되고, "코드 변경 0"이 깨진다.
`var-14`가 이 분리를 강제한다 — 이 케이스는 `CORNER_KICK`을 **채택하지 않았다고 말하기 위해** 그 이름을 알아야 한다.
유효한 값의 목록(어휘)과 지금 열려 있는 값의 목록(활성 집합)은 같은 것이 아니다.
`shared-types`에 첫 파일이 들어가는 커밋에서 어휘의 정의가 README에서 그 파일로 넘어간다.
두 소유자가 겹치는 기간을 두지 않는다 (README 8절 "값의 정의는 어디에 있는가").
2차 경고 퇴장이 실제 사례다. IFAB는 검토 범주에서 `not second yellow card/caution`으로 명시 배제하고, 대회요강은 "퇴장 상황"이라고만 쓰고 배제 문구가 없다.
어느 쪽이 맞는지 판단할 근거가 우리에게 없다. **갈린다는 사실 자체가 답**이므로 그대로 싣는다.

FR-10은 이전 판에서 "4개 검토 범주"와 "사실적/주관적 구분"을 한 요구사항에 묶어 두었다.
둘은 다른 층위다. 범주는 **검토 가능 여부**를 정하고, 사실적/주관적은 **검토 절차**(OFR인지 VAR 단독인지)를 정한다.
어느 쪽도 개입 문턱을 낮추거나 높이지 않는다. FR-10을 게이트 단위로 쪼갠 이유가 이것이다.

FR-12는 이전 판에서 "판본 경계 경기일(6/30 vs 7/1)에 서로 다른 판본이 선택됨"이었다.
**한 시즌이 IFAB 판본 경계를 관통한다는 전제가 잘못됐다.** 대회요강은 시즌 전체에 하나의 판본을 지목한다.
경계 테스트는 삭제하고, 대신 판본 차이가 데이터로 반영되는지를 FR-21로 검증한다.
2026/27에서 VAR 검토 범주가 실제로 4→5로 늘어났으므로 이 테스트는 가상의 사례가 아니다.

**4→5를 만든 것은 코너킥이지 2차 경고가 아니다.**
2차 경고는 범주 `c`가 `Direct red cards (not second yellow card/caution)`에서 `Red cards`로
이름이 바뀌면서 **그 안의 불릿으로** 들어왔다. 범주 수를 늘린 것은 신설된 `e. Clearly incorrectly
awarded corner kick ... (competition option)`이다.

두 변경을 구분하지 않으면 FR-21의 검증이 틀린 것을 확인하게 된다.
그래서 픽스처가 둘을 따로 고정한다 — `var-12`/`var-13`은 2차 경고가 **같은 범주 안에서** 넓어지는지를,
`var-14`/`var-15`/`var-16`은 코너킥이 **범주로 신설되고 대회 채택 축이 따로 있는지**를 본다.

FR-24가 필요한 이유가 여기 있다. `competition option`은 IFAB가 열어둔 것이고 대회가 채택해야 켜진다.
판본만 보고 `reviewable`을 켜면 **채택하지 않은 대회에서 없는 권한을 만들어낸다.**
K리그의 실제 채택 여부는 아직 확인되지 않았으므로(미결 질문 #5) 어느 쪽도 사실로 주장하지 않고
각 경우의 동작만 고정한다.

| 항목 | 기준 | 측정 방법 |
|---|---|---|

### 6.3 폴더 구조

1단계에서 실제로 생성하는 범위만 표시한다.

```
project/
├── packages/
│   ├── rule-engine/          ← 1단계 핵심
│   │   ├── src/
│   │   │   ├── interpreter.ts
│   │   │   ├── evaluate-push.ts
│   │   │   ├── var-assessment.ts     ← 4게이트
│   │   │   ├── speed-gate.ts         ← 관측 속도 검사
│   │   │   ├── fact-signature.ts
│   │   │   └── types.ts              ← Observed<T>, Decision
│   │   ├── fixtures/         ← 케이스 27 + 불변식 4 (작성 완료)
│   │   └── test/
│   ├── rule-data/            ← 판본별 규칙 정의 JSON
│   │   ├── 2025-26/
│   │   └── 2026-27/          ← FR-21 대조군. 범주 5개
│   ├── database/             ← 스키마 4개 테이블
│   └── shared-types/
│
├── rules/                    ← 원문 + metadata.json
│
└── docs/                     ← PDCA 문서
```

`rule-data/2026-27/`을 1단계에 넣는 이유는 FR-21 때문이다.
판본이 하나뿐이면 "데이터로 분리했다"는 주장을 검증할 방법이 없다.
두 판본이 실제로 다른 값을 내야 분리가 증명된다.

> **위 트리는 설계 문서가 정정했다.** `rule-data/`는 판본이 아니라 **권위**를 최상위로 두고
> (`ifab/2025-26/`), `rule-engine/src/`의 파일 이름 네 개도 바뀌었다.
> 현재 유효한 배치는 [설계 문서 5.2·6.3](../../02-design/features/규정-데이터-룰엔진.design.md)이다.

`apps/web/`, `workers/video/`, `scripts/parse-*`는 1단계에서 생성하지 않는다.

설계 문서에서 먼저 결정해야 할 것은 **`Observed<T>`의 경계**다.
모든 사실값을 래핑할지, 속도에 민감한 값만 래핑할지에 따라 스키마와 테스트 양이 크게 달라진다.
현재 계획은 전부 래핑 쪽이다 — 예외를 두면 어떤 값이 예외인지가 또 하나의 규칙이 된다.

> **설계 문서 7절이 답했다.** 관측된 사실은 전부 래핑하고 **관측 조건은 래핑하지 않는다.**
> `cameraSufficiency`는 예외 목록의 한 항목이 아니라 관측 조건 그 자체이며,
> 래핑하면 자기 자신의 관측 조건을 물어야 해서 끝나지 않는다. 이 선을 그으면 예외 목록이 생기지 않는다.

### 확인이 필요한 미해결 사항

| # | 질문 | 상태 | 확인 방법 | 차단 대상 |
|:-:|---|---|---|---|
| ~~1~~ | ~~K리그가 시즌 중 IFAB 판본을 전환하는가~~ | **종료** | 대회요강 원문 확인 완료. 시즌 전체에 단일 판본 적용 | — |
| 1a | 대회요강의 판본 지정이 문서 전체에 미치는가, 뇌진탕 교체 본조에만 미치는가 | 미해결 | 연맹 문의 | FR-03 `verification` |

| 5 | K리그가 2026/27 코너킥 검토 범주(`competition option`)를 채택하는가 | 미해결 | 2027 대회요강 공개 시 확인 | FR-24 (기본값) |

1번은 원문 대조로 닫혔다. 대회요강은 시즌 전체에 하나의 IFAB 판본을 지목하며,
"판본 경계를 관통하는 시즌"은 존재하지 않는다. 이에 따라 FR-12를 다시 썼다.

**다만 1a가 새로 열렸다.** 원문에서 판본을 명시적으로 지정한 문구는 뇌진탕 교체 조항 안에 있고
그 조항의 본조에 한정되는 표현이다. 문서 전체에 같은 판본이 적용된다는 것은 **합리적이지만 추론**이다.
따라서 매핑을 비워 두지는 않되 `verification: INFERRED`를 결과에 그대로 노출한다.

비워 두는 것과 추정으로 채우는 것 사이에 세 번째 선택지가 있다 — **채우되 채웠다고 말하는 것**이다.

**5번은 답이 나올 때까지 기본값을 정하지 않는다.** 미채택으로 두면 K리그가 채택했을 때 조용히 틀리고,
채택으로 두면 아직 열리지 않은 권한을 만들어낸다. 그래서 `competition_options`를 명시적 입력으로 두고,
값이 없으면 `UNKNOWN_COMPETITION_OPTION`을 반환한다 — 판본 매핑에서 `UNKNOWN_RULE_VERSION`을 쓰는 것과 같은 이유다.

이 질문은 2026/27 판본이 K리그에 실제로 적용되기 전까지는 아무것도 차단하지 않는다.
지금 픽스처가 하는 일은 그날 무엇을 확인해야 하는지를 남겨두는 것이다.

### 0.6 변경 요약

설계 문서가 열린 항목 셋을 닫았고, 그 결과 이 문서의 세 곳이 낡았다. 지운 것이 아니라 **어디가 유효한지 표시**했다.

- **ORM** — `Drizzle (잠정)` → **확정**. FR-29의 JSONB `CHECK`과 생성 열을 스키마 정의 한 곳에 둘 수 있는 쪽 ([설계 8.2](../../02-design/features/규정-데이터-룰엔진.design.md))
- **6.3 폴더 구조** — `rule-data/`가 판본이 아니라 **권위** 우선(`ifab/2025-26/`). `accounts[]`가 계층별이라 판본만으로는 주소가 나오지 않는다. `rule-engine/src/`의 파일 네 개도 바뀌었고 `types.ts`는 `shared-types`로 간다 (설계 5.2·6.3)
- **`Observed<T>` 경계** — 8절이 설계에서 먼저 정하라고 지목한 항목. 관측된 사실은 전부 래핑, **관측 조건은 래핑하지 않는다**. 예외 목록이 아니라 선 하나다 (설계 7)
- **검사 6** — 설계 문서 4.2가 어휘를 세 번째로 적는 자리가 되었으므로, `vocabulary.ts` 스케치 8개를 README와 기계로 묶었다. 값 불일치와 README가 모르는 어휘 둘 다 음성 테스트로 확인함

### 0.5 변경 요약

**JSON 여섯 기준을 데이터에 적용함** (픽스처·라벨 사례 122건)

- 키를 snake_case로 통일. `given.facts`의 camelCase 17종
- `threshold_met`의 `TRUE`/`FALSE` → `MET`/`NOT_MET`. 3값 열거형을 불리언처럼 적고 있었다
- `cases[]`에서 `invariants[]`를 분리. 사후 검사는 실행이 아니므로 같은 배열에 있으면 안 된다
- 단일키 래퍼와 `_role`·`_meaning` 제거. 구조가 설명을 대신하게 했다

**SSOT의 소유자를 확정함** (FR-28)

DB 컬럼은 SSOT가 될 수 없다. 값 집합이 판본에 따라 다르고(`var-12`/`var-13`),
결과가 JSONB 안에 있으며, 픽스처 검사가 DB 없이 돌아가야 하기 때문이다.

| 무엇 | SSOT |
|---|---|
| 어휘 — 판본과 무관한 낱말의 닫힌 집합 | `packages/shared-types` |
| 활성 집합 — 그 판본·대회에서 열려 있는 부분집합 | `packages/rule-data` |
| 구조 불변식 — 행이 성립하려면 참이어야 하는 것 | DB `CHECK`·제약 |

`shared-types`가 빌 동안은 README가 어휘의 정의이고, 첫 파일이 들어가는 커밋에서 방향이 뒤집힌다.
그동안의 중복은 `check/readme.mjs` 검사 5가 막는다.

**`authority` 이름 충돌을 갈랐다.** `rules.authority`(규정을 쓴 주체)와
`official_verdicts.authority`(사건을 판단해 발표한 주체)가 한 이름을 쓰고 있었다.
후자를 `announced_by`(분류) + `announced_by_name`(발표문 표기 그대로)으로 나눴다.

**인용을 JSONB 스냅샷으로 옮겼다** (FR-29). `decision_rule_citations` 테이블을 없앤다.
`rule_id` 외래키는 조항 텍스트가 나중에 고쳐지면 예전 결과의 근거를 조용히 바꾼다.

### 0.4 변경 요약

**산출물의 형태가 바뀜**

이 시스템이 답하는 질문을 "이 판정이 맞았나"에서 "이 상황에 대해 규정은 무엇을 말하는가"로 옮겼다.
`decision_match`는 삭제하지 않고 참고 필드로 내렸다. 없애면 맞는 판정과 틀린 판정을 구분할 수 없어지는데, 그건 규정을 넣은 이유 자체를 버리는 것이기 때문이다.

바뀐 것은 무엇을 **먼저** 보여주는가다. `accounts`가 앞에 오고 `decision_match`가 뒤에 온다 (FR-07).

- FR-26 — 사실이 막혀도 `accounts`는 나온다. `push-10`이 이것을 고정한다
- FR-27 — 층위가 갈리면 그대로 싣는다. 2차 경고 퇴장이 실제 사례다

### 0.3 변경 요약

**틀린 귀속을 정정함**

- 2026/27 VAR 범주가 4→5로 늘어난 원인을 `clearly incorrect second caution`으로 적었던 것을 정정.
  실제로는 신설된 `e. Clearly incorrectly awarded corner kick ... (competition option)`이며,
  2차 경고는 범주 `c`의 이름이 `Red cards`로 바뀌면서 **그 안의 불릿으로** 들어왔다
- 이에 따라 FR-24 신설. `competition option`은 판본과 별개의 축이다

**테스트 데이터를 둘로 나눔**

- 합성 픽스처(`packages/rule-engine/fixtures/`) — 규칙 적용의 정확성, PASS/FAIL, 케이스 27 + 불변식 4
- 라벨 사례(`datasets/labeled-cases/`) — 현실 정합성, 점수, 3건
- 이유: 실제 사례의 입력은 3단계부터 파이프라인이 생성하므로 **입력 고정이라는 회귀 테스트의 전제가 성립하지 않는다.**
  추출을 개선하면 같은 경기에서 다른 값이 나오고, 그때 깨지는 테스트는 개선을 실패로 신고한다
- 실제 사건은 픽스처를 **낳지만** 픽스처가 되지는 않는다. 연결은 `derived_from` / `derived_fixtures`로 남긴다

**구현 없이 도는 검사 2종 추가**

- `check/enums.mjs` — 픽스처가 문서에 없는 열거형을 쓰면 실패. 스키마가 먼저다
- `check/links.mjs` — 갈라놓은 두 디렉터리의 상호 참조가 끊기면 실패
- `check/json.mjs` — 키 네이밍·타입 정직·깊이·배열 동질성·날짜·단일키 래핑. 판정선은 이 저장소 데이터로 맞췄고 근거 없는 규칙은 넣지 않았다
- `check/readme.mjs` — 문서를 하나로 합친 대가가 내부 참조이므로 그것만 자동으로 막는다. 8절과 11절에 같은 이름으로 적힌 열거형의 값이 갈리면 실패하고, 설계 문서의 `vocabulary.ts` 스케치가 README와 갈려도 실패한다 (SSOT가 README에 있는 동안의 중복 방지)
  실제로 `RuleCitation`이 네 곳에서 쓰이면서 정의가 없었고, 이 검사기가 그것을 찾았다
